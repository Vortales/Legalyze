# Legalyze 1.0.5 — Universal v7: реальная запись голоса и защита от отправки пустого запроса

Эталонная папка решения (анализ + лучшее решение). Рабочая логика Win10/Win11,
серверное взаимодействие, авторизация и основной GUI не менялись. Папки
`TestLegalUniversal/`, `TestLegalUniversal_v2/`, `TestLegalUniversal_v3/`,
`TestLegalUniversal_v4/`, `TestLegalUniversal_v5/`, `TestLegalUniversal_v6/`
остаются нетронутыми как резервные копии; каждая новая правка выходит в новой
версионной папке `TestLegalUniversal_vN` (эта — `TestLegalUniversal_v7`).

**v7** исправляет дефект из присланного лога Windows 10 (pid 17540,
`universal-embedded-v6`): **нажатие «Микрофон»/F3 мгновенно показывало
«Речь не распознана» и отправляло запрос в чат ИИ без всякой записи голоса.**
Причина не угадана, а прочитана из лога: процесс-хост диктовки завершался
через 310 мс с кодом 2 и пустым stderr.

Всё, что было сделано раньше, сохранено: нативный `SpeechRecognition`
отключён (он ронял рендер), сырой браузер при старте не виден, зум 67%,
хоткеи F2/F3, прикрепление файлов без Ctrl+R (v6), полное руководство по
onefile-сборке EXE (v5, § 7).

## 1. Анализ причин дефектов

### Горячие клавиши: почему не срабатывали и всегда «конфликт»

Прежняя реализация (`win32_hotkeys.py`) строила **отдельный поток с невидимым
окном**: `CreateWindowExW` + `RegisterClassW` + цикл `PeekMessageW` +
`RegisterHotKey`, а события перекидывала в Qt сигналом из другого потока. Любая
ошибка в этом длинном пути (обрезание HWND/HINSTANCE на Win64 из-за
отсутствующих `argtypes`/`restype`, отказ `RegisterClassW`/`CreateWindowExW`,
гибель потока-демона) давала ровно наблюдаемую картину:

* `set_keys()` возвращал `False` → статус **«Конфликт горячих клавиш» при
  любой смене клавиши** (хотя конфликта не было);
* события не приходили вообще: поток мёртв → ни `WM_HOTKEY`, ни опрос.

**Решение (v2):** события клавиш получает **главный поток Qt** — `QTimer` (25
мс) вызывает `HotkeyMonitor.tick()`, который опрашивает `GetAsyncKeyState`
(с корректными `argtypes`/`restype`), детектирует фронт нажатия и сразу в
контексте GUI вызывает обработчик. Никаких потоков, скрытых окон, очередей
сообщений и маршалинга сигналов — отказаться не от чего. Это работает с любым
фокусом, поверх других окон и независимо от раскладки (физическое состояние
клавиатуры). Антидребезг — 350 мс на каждую клавишу отдельно.

`RegisterHotKey` сохранён **только как best-effort подавление** проброса
клавиши в другие приложения (чтобы F3 не попадал в браузер). Его отказ ничего
не блокирует и нигде не отображается: статус после смены клавиш всегда
«Готов к работе», ложный «Конфликт горячих клавиш» невозможен по построению.

### Микрофон: нажатие вызывало «Восстановление ИИ»

Симптомы (лог 2026-09-30): нажатие «Микрофон»/F3 → статус «Восстановление
ИИ…» вместо диктовки; повторное нажатие — снова восстановление.

Причина (по логу, **не** getUserMedia): `mic.dictation_started` → через 18 мс
`webengine.render_terminated CrashedTerminationStatus` → `crash_recovery`.
Рендер падал при `rec.start()` на **нативном** `window.SpeechRecognition`:
QtWebEngine 6.11 / Chromium 140 экспортирует конструктор, но штатный движок
распознавания требует Google API-ключа (`speech_recognition.cc`), которого нет
в этой поставке — старт распознавания убивает дочерний процесс. Штатная кнопка
микрофона сайта именно его и вызывала. Шим v3 намеренно не трогал нативный
конструктор («веб-STT не используем») — но его использует **сайт**.

Решение (v4), слоями:

1. **Шим всегда перехватывает `SpeechRecognition`/`webkitSpeechRecognition`:**
   нативный конструктор сохраняется в `window.__legalyzeNativeSpeechRecognition`
   (только диагностика) и **никогда не вызывается**; поверх ставится наш класс
   `window.LegalyzeSpeechRecognition` (QWebChannel → Windows System.Speech).
   Тест: нативный mock с `start() { throw }` — не вызывается ни разу.
2. **Перехват всех кликов по любой кнопке микрофона** (штатной или реплики):
   события pointer/mouse/click перехватываются в capture-фазе ДО обработчиков
   сайта (`preventDefault` + `stopImmediatePropagation`) и уводятся в
   НАСТОЯЩУЮ диктовку. Сайт не получает ни одного события → его
   `getUserMedia`/`SpeechRecognition` не вызываются → рендер не падает.
   Штатная кнопка микрофона остаётся на виду и реально работает.
3. **F3 сначала запускает нашу диктовку напрямую** (`JS_MIC_TOGGLE`); повторное
   нажатие/«Отправить»/Enter останавливает запись и отправляет запрос.
4. **Автовосстановление при сбое рендера** (до 3 раз) с остановкой висящих
   потоков, долбивших мёртвый CDP-сокет (шум `WebSocketConnectionClosed…`).
5. **Понятный статус** «Страница ещё загружается — подождите…», если микрофон
   нажат до готовности чата.

### Микрофон v7: «Речь не распознана» и отправка без записи

Симптом (лог Windows 10, 2026-09-30, `universal-embedded-v6`):

```
22:42:51.333  speech.request      lang=ru
22:42:51.351  speech.started      lang=ru-RU
22:42:51.660  speech.host_exit    code=2  stderr=""      <-- через 310 мс
...
22:42:54.9xx  Input.dispatchMouseEvent x3                 <-- «второе нажатие»
22:43:00.678  DecrementWorker -> POST /api/client/queries <-- ушёл пустой запрос
```

Ни одного `speech.hypothesis`/`speech.result`: хост диктовки умирал, не успев
передать ни события. Код 2 — это `exit 2` из нашего же PowerShell-скрипта:

```powershell
try {
  $rc = New-Object System.Speech.Recognition.SpeechRecognitionEngine($cult)
} catch {
  Emit @{ type = 'error'; code = 'language-not-supported' }; exit 2
}
```

то есть **движок не создался**. `System.Speech` бросает
`No recognizer of the required ID found`, когда в Windows не зарегистрирован
распознаватель запрошенной культуры (ru-RU), — а скрипт v6 создавал движок
«вслепую», по культуре, которую передала страница. Второй кандидат: сборка
`System.Speech` вообще не попала в контекст загрузки (`Add-Type` в
`-NonInteractive` хосте), тогда тип просто не существует — тоже `exit 2`.

Дальше срабатывала цепочка, и именно она давала наблюдаемую картину:

1. Хост умер, не emit'ив ничего → поток чтения увидел EOF → `no-speech`.
2. GUI показал «Речь не распознана — повторите (F3)», но `mic_active`
   остался `True`.
3. Следующее нажатие ушло в ветку «2-е нажатие» = **стоп + отправка**, и в
   чат ушёл пустой запрос (в логе — `DecrementWorker`).

И отдельная, более глубокая проблема: даже если бы хост выжил, **события .NET
в `-NonInteractive` хосте PowerShell не доставляются** — движок ждал
`add_SpeechRecognized` + насос событий (`Start-Sleep` / `DoEvents`), а
PowerShell запускает такие обработчики только когда runspace прокачивает
очередь событий. Этим объясняется полное отсутствие событий и в v5.

**Решение (v7), по пунктам:**

1. **Сначала спрашиваем Windows, что есть, потом создаём движок.**
   `InstalledRecognizers()` → список уходит в лог (`speech.recognizers`),
   дальше выбирается: точная культура → любой распознаватель того же языка →
   первый доступный вообще (событие `speech.lang_fallback`). Машина только с
   en-US больше не умирает, а записывает и честно пишет в статусе, что
   распознаватель не русский.
2. **Цепочка загрузки сборки**: `Add-Type` → `LoadWithPartialName` →
   `LoadFrom` рядом с CLR (`GetRuntimeDirectory()`). Если `System.Speech`
   действительно недоступен — понятная ошибка `service-not-allowed`, а не
   пустой `exit 2`.
3. **Синхронный цикл `Recognize()`** вместо .NET-событий и насоса: это
   блокирующий вызов, ему не нужен pump, не нужен Windows.Forms, нечего
   ломать. Один вызов — одна фраза; цикл делает диктовку непрерывной.
   Явные таймауты: `InitialSilenceTimeout` 15 с, `EndSilenceTimeout` 800 мс.
4. **Каждая ошибка уходит с настоящим текстом .NET-исключения** (поле `msg` →
   `speech.error` в логе) — причина больше не теряется.
5. **Отправка только при наличии распознанного текста.** Повторное нажатие
   при пустой диктовке не отправляет ничего: `mic.cancelled_no_text`, статус
   «Запись не началась — нажмите «Микрофон» ещё раз». Любая «мёртвая»
   диктовка снимает `mic_active` (`_mic_reset_state`), поэтому следующее
   нажатие снова **начинает** запись.
6. **Понятные русские статусы**: нет распознавателя речи в Windows, нет
   микрофона, нет доступа к микрофону, распознаватель подменён (fallback).
7. **Сторож «родитель умер»**: хост сам выходит, если процесс приложения
   исчез, — микрофон не остаётся занятым осиротевшим `powershell.exe`.

### Сырой браузер виден при запуске («нету поверх него GUI»)

Причина: шторка (`browser_cover`) создаётся в конструкторе окна, а браузер —
позже в `_start_chrome`; Qt кладёт более поздних детей **поверх** ранних, и
шторка оказывалась под web-виджетом. В v4 `_show_overlay` и `_start_chrome`
вызывают `browser_cover.raise_()`: до раскрытия по готовности (`loadFinished` +
250 мс) пользователь видит только шторку приложения, затем — уже зачищенную
страницу. Видимость элементов браузера исключена.

### Скрипты страницы: ошибка сборки «not a function» и глухой голосовой мост

IIFE-чанки бандла склеивались переводом строки; `})()` перед следующим чанком
`(() => …` разбирался как вызов → TypeError → хвост бандла (инициализация
QWebChannel) не выполнялся → `window.__legalyzeSpeechBridge` не создавался.
В v4 чанки склеиваются через `";\n"`, IIFE закрываются `;` — покрыто тестом.

### «Вечная прогрузка» на чистом %APPDATA%

Свежий профиль Google показывает межстраничник согласия, который прятался без
принятия и оставлял «вечную прогрузку». Теперь `CONSENT_AUTOCLICK_JS` нажимает
только кнопки согласия («Принять все»/Accept) и лишь затем элемент скрывается.

### Мигание элементов при запуске

Всё внедряется на `DocumentCreation` одним бандлом (UA/brand, голосовой мост,
автосогласие, рабочая кнопка микрофона, зачистка лишнего, канал Qt): лишние
элементы не появляются вовсе — приложение выглядит как сайт, а не как браузер.

## 2. Голос (как работает)

1. F3 (или кнопка микрофона) → штатный сценарий сайта находит кнопку
   микрофона (штатную или нашу реплику) и «кликает» её.
2. Наш мост QWebChannel (`legalyzeSpeech`) запускает диктовку Windows
   (`System.Speech`): хост сам выбирает **реально установленный**
   распознаватель (см. § 1) и стримит распознанные фразы. Никаких событийных
   насосов PowerShell — синхронный цикл распознавания.
3. `SpeechRecognition`-шим пишет текст в поле ввода (`textarea.ITIRGe` /
   `aria-label="Задайте вопрос"`).
4. Повторный F3 → штатный сценарий нажимает кнопку отправки (или Enter) —
   запрос уходит в чат ИИ. **Но только если диктовка дала текст**: при пустой
   записи повторное нажатие ничего не отправляет, а начинает запись заново.
   Пустой запрос в чат невозможен по построению.

Всё CSP-безопасно: только QWebChannel, без сетевых мостов. Если мост
недоступен — понятная ошибка через шим, без падений.

## 3. Почему эта архитектура

* Chromium/QtWebEngine без Google API-ключа **не умеет** штатный
  SpeechRecognition, и его `start()` даже **роняет рендер-процесс** (проверено
  по исходникам Chromium: `speech_recognition.cc` требует API key, и по логам
  пользователя) — поэтому наш шим **всегда** перехватывает конструктор, а
  распознавание идёт через Windows System.Speech;
  поэтому диктовка всегда идёт через Windows System.Speech.
* Нативное окно QtWebEngine обычно строится без WebRTC → `getUserMedia`
  недоступен (QTBUG-55108) — веб-диктовка сайта всё равно не заработала бы.
* Опрос `GetAsyncKeyState` из главного потока — единственный механизм хоткеев,
  у которого нет окна, потока и очереди сообщений, т.е. нечему ломаться.

## 4. Установка и запуск (Windows 10/11 x64)

```
py -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python main.py
```

`PyQt6-WebChannel` **не нужен** (не существует на PyPI): `PyQt6.QtWebChannel`
входит в базовый пакет PyQt6. При отсутствии официального `qwebchannel.js`
автоматически включается встроенная облегчённая реализация протокола.

### Быстрая проверка без входа в Google

```
.venv\Scripts\python smoke_browser.py
```

Локальная тест-страница проверяет: готовность страницы, поиск/клик кнопки
микрофона, поверхность Web Speech API, вставку реплики кнопки микрофона,
зум 67% (2/3). Exit code 0 = всё прошло.

### Автотесты

```
py -m unittest discover -s tests -v
```

56 тестов: чистота поставки, неизменность бизнес-логики (байт-в-байт с
`TestLegal`/`TestLegalQtWebEngine`), корневые причины, опрос горячих клавиш
(фронт + антидребезг на клавишу), реплика кнопки микрофона (инъекция,
диктовка в поле ввода, остановка по отправке, приоритет штатной кнопки),
шим речи, зачистка DOM, автосогласие, протокол QWebChannel, эталонный
onefile-синтаксис, регрессы v6 (идемпотентный старт диктовки, конкретная
культура речи, hardened PowerShell-скрипт, события хоста доходят до страницы,
явный старт микрофона, обновление CDP-соединения в потоке выгрузки) и новые
регрессы v7: распознаватель ищется до создания движка, у каждой ошибки хоста
есть реальный текст причины, цикл распознавания не зависит от насоса событий,
цепочка загрузки сборки, ошибка хоста не подменяется на `no-speech`,
fallback-язык сообщается пользователю, микрофон никогда не отправляет пустой
запрос, упавшая диктовка снимает состояние записи.

Логика авторизации, взаимодействие с сервером, основной GUI, выгрузка файлов,

## 6. Что улучшено дополнительно

* Зум окна нативно 67% (`ZOOM_FACTOR = 2/3`), применяется и после каждой
  загрузки страницы.
* Логотип Google скрыт; интерфейс выглядит как сайт, а не как браузер.

## 7. Сборка EXE (Nuitka)

### 7.1. Подготовка (Windows 10/11 x64)

1. Установить **64-битный Python 3.11+** и **Visual Studio Build Tools**
   (компонент «Средства разработки C++»). При отсутствии MSVC можно собрать
   ключом `--mingw64` (Nuitka сам скачает компилятор), но эталонная сборка
   шла через MSVC.
2. В папке решения:

```bat
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-build.txt
```

`requirements-build.txt` включает `requirements.txt` (PyQt6, PyQt6-WebEngine,
requests, websocket-client, cryptography, fpdf2) и Nuitka с зависимостями
сборки. Других пакетов не нужно: диктовка — штатный PowerShell +
.NET System.Speech (Windows 10/11).

### 7.2. Релизная сборка — ONEFILE (эталонный синтаксис)

**Команда дословно из `release_reference/BUILD_COMMAND.txt`** (проверенная
ранее рабочая форма, ничего не удалять):

```bat
python -m nuitka --onefile --windows-console-mode=disable --enable-plugin=pyqt6 --include-package=requests --include-package=websocket --include-package=cryptography --include-package=fpdf --include-data-file=data/DejaVuSans.ttf=data/DejaVuSans.ttf --windows-icon-from-ico=icon.ico --assume-yes-for-downloads --output-dir=build --output-filename=Legalyze.exe main.py
```

Практически: просто выполните **`build_nuitka.bat`** — он выполняет ту же
команду (флаги и порядок сохранены) и добавляет только лицензию шрифта
`FONT-LICENSE.txt` и метаданные версии файла (`1.0.5.0`), затем проверяет,
что `build\Legalyze.exe` появился.

Результат: **`build\Legalyze.exe` — один самодостаточный файл** (Python,
QtWebEngine, шрифты внутри). Окно консоли отключено, иконка и версия в
свойствах файла проставлены. Админ-манифест не добавляется, логика не
меняется.

### 7.3. Отладочная сборка — standalone (по необходимости)

`build_nuitka_standalone.bat` собирает папку `build\main.dist\` (EXE +
DLL/ресурсы рядом). Удобно для отладки и диагностики; для релиза используйте
onefile. При выдаче standalone раздавайте **все** файлы папки
(включая `QtWebEngineProcess.exe`, ресурсы и locales).

### 7.4. Что делать после компиляции

1. **Проверьте EXE** на сборочной машине: запуск без установленного Python,
   окно приложения поднимается, страница ИИ загружается в GUI.
2. **Развертывание** — скопируйте `Legalyze.exe` (onefile) в целевую папку.
   Рядом ничего класть не нужно: `config.json`, `Шаблон.txt`, логи и профиль
   встроенного браузера живут в `%APPDATA%\Legalyze` (первый запуск создаёт
   их сам). При обновлении старой установки, где `config.json` лежал рядом со
   старым exe, он **однократно мигрируется** в `%APPDATA%\Legalyze`
   автоматически. Если готовите `config.json`/`Шаблон.txt` заранее — положите
   их в `%APPDATA%\Legalyze` **до** первого запуска (ТЗ 1.1–1.2).
3. **Проверка на чистой машине** под обычным пользователем (без прав
   администратора): вход, промт с микрофона, выгрузка файлов — по чек-листу
   п. 8. Логи диагностики смотрите в `%APPDATA%\Legalyze\logs`.
4. **Антивирусы/SmartScreen**: неподписанные EXE нового проекта вызывают
   предупреждения репутации — это нормально. Легальные способы (прозрачная
   упаковка, подписание, накопление репутации) описаны в папке `TestLegal`;
   иных обходов не используйте и не требуется.
5. **Версия сервера**: `config.json` — версия **1.0.5** (сервер 1.0.4,
   контракт не менялся). Автообновление (`updater.py`) работает как раньше.

## 7.5. Подтверждение готовности

* Все модули на месте: бизнес-логика (`config`, `crypto_utils`, `hwid_gen`,
  `secure_store`, `storage_paths`, `updater`) **байт-в-байт** как в рабочей
  версии (контролируется тестами); интерфейс, поля ввода/вывода, выгрузка
  файлов, авторизация и серверное взаимодействие не менялись.
* Голос: диктовка Windows System.Speech через наш мост; распознаватель
  выбирается среди реально установленных в Windows (`speech.recognizers`),
  при отсутствии нужного языка работает fallback с честным статусом
  (`speech.lang_fallback`); нативный `SpeechRecognition` (крашил рендер)
  отключён; первое нажатие микрофона/F3 — запись, второе — остановка и
  отправка промта **только если есть распознанный текст**; статус диктовки
  виден, причина отказа видна пользователю.
* Файлы: поток выгрузки переживает навигацию страницы (актуальное CDP-соединение)
  — ручной Ctrl+R больше не нужен.
* Хоткеи F2/F3 — с любого фокуса и раскладки.
* **Автотесты: 56/56 (stdlib + Node)** — включая регресс-тест «нативный
  SpeechRecognition никогда не вызывается», тесты ASI-склейки бандла, шторки
  поверх браузера, эталонного onefile-синтаксиса, тесты v6 и новые тесты v7.
* Окончательное подтверждение — запуск собранного EXE на ваших Windows 10 и
  11 по чек-листу п. 8 (в особенности п. 5 и 6 — микрофон и отсутствие сырого
  браузера при старте).

## 8. Чек-лист приёмки на Windows 10 и 11

1. Зум 67% восстановлен; логотип скрыт; запуск без миганий.
2. F2 скрыть/показать окно — работает с любого фокуса и любой раскладки.
3. F3 — запись голоса: статус «Слушаю… говорите», текст идёт в поле ввода;
   повторный F3 отправляет запрос в чат ИИ. Если запись не удалась —
   «Запись не началась…» и **никакой отправки**.
4. Смена клавиш — статус «Готов к работе» (без «Конфликт горячих клавиш»).
5. Кнопка микрофона в панели ввода видна и работает (клик = запись и отправка
   промта); после нажатия статус «Запись голоса…», **не** «Восстановление ИИ».
6. Во время «Ожидание страницы ИИ…» элементы браузера не видны (только шторка
   приложения) — сырой браузер при старте не появляется.
7. Первый запрос на чистом профиле работает без ручного согласия.
8. Загрузка/выгрузка файлов, вход, поля — как в рабочей версии.
9. **Файлы прикрепляются сами**, без Ctrl+R: в логе (`%APPDATA%\Legalyze\logs`)
   не должно быть `upload.failed`; при дозагрузке страницы появляется
   `upload.page_refreshed`, а затем `upload.attachments_confirmed: true`.
10. **Запись голоса реальна**: после нажатия в логе идут `speech.started`,
   затем `speech.result` при речи. Если хост всё же падает — видно
   `speech.host_exit` с кодом и хвостом stderr и `speech.error` с настоящим
   текстом причины (раньше смерть была немой).
   `speech.start_ignored` — это норма: повторный старт не перезапускает живой
   хост.
11. **Диагностика распознавателя**: в логе есть `speech.recognizers` со
   списком реально установленных в Windows распознавателей (например
   `langs=en-US`) и запрошенным языком (`want=ru-RU`). Если нужного языка
   нет — появится `speech.lang_fallback`, а в статусе приложения будет прямо
   сказано, чем распознаётся речь и что установить.
12. **Пустая отправка невозможна**: нажмите «Микрофон»/F3 дважды подряд, не
   говоря ничего, — запрос в чат уходить не должен (в логе
   `mic.cancelled_no_text` / `mic.speech_error`, в статусе — причина).

## 9. Известные ограничения

* Автоматизация зависит от DOM/логина/сети Google — при редизайне сайта
  селекторы нужно обновить (проверяйте диагностику в `%APPDATA%\Legalyze\logs`).
* Качество распознавания Windows System.Speech уступает Google ASR; для
  лучшего качества говорите чётко, в тихой комнате.
*Диктовка требует установленного в Windows распознавателя речи*
(**Параметры → Время и язык → Речь / Язык**): для русского — русский речевой
пакет. Если его нет, приложение не «молча умирает», а сообщает об этом и
(по возможности) работает на доступном языке — смотрите `speech.recognizers`
в логе.
* Подавление проброса F2/F3 в другие программы — best-effort (если
  `RegisterHotKey` занят другим приложением, хоткеи клиента всё равно
  работают, но клавиша может достаться и фоновой программе).
* Штатный Web Speech API/getUserMedia в этой поставке QtWebEngine неработоспособен
  (и ронял рендер) — диктовка всегда идёт через Windows System.Speech через наш
  мост; при сбое рендера страница автоматически перезагружается (до 3 раз).
