# Legalyze 1.0.5 — Universal: встроенный браузер + голос + горячие клавиши

**Рекомендуемая версия.** Отдельная папка: `release`, `release_reference`, `TestLegal`, `TestLegalQtWebEngine` и `clientwin11` не изменены. Основа — вариант `TestLegalQtWebEngine`, который вы проверили (авторизация, GUI, браузер, файлы, запросы и ответы работают), плюс устранение двух его недостатков:

1. **не работали глобальные горячие клавиши** (скрытие окна и начало/конец голосового ввода);
2. **не было кнопки микрофона** в странице чата.

Логика авторизации, взаимодействие с сервером Legalyze, внешний вид GUI, подготовка промтов, экспорт PDF/TXT, запросы/ответы и списание баланса **не изменены** — это подтверждено тестами (байт-в-байт сравнение бизнес-модулей и worker-классов).

## 1. Анализ: почему два элемента не работали

### Микрофон
Кнопка микрофона — часть **сайта ИИ**. Сайт рисует её только когда в браузере есть Web Speech API (`window.SpeechRecognition` / `webkitSpeechRecognition`), то есть готовый движок распознавания речи. В настоящем Chrome распознавание — **облачный сервис Google, привязанный к проприетарным ключам Chrome**: open-source Chromium (и построенный на нём Qt WebEngine) содержит только «обёртку» API без рабочего сервиса, поэтому:

- в вашем portable-Chrome кнопка была (сервис есть);
- в Qt WebEngine её нет — сайт не рисует кнопку, горячая клавиша не находит её в DOM.

Это подтверждено поведением сайта в других «embedded»-браузерах (Electron, webview): кнопка скрыта, `SpeechRecognition` отсутствует или не работает. Веб-страница с пустым файлом `html микрофон кнопка.txt` из корня проекта — прямое следствие этой же проблемы.

### Горячие клавиши
Старая схема: `RegisterHotKey` на HWND главного Qt-окна + приём `WM_HOTKEY` через `nativeEvent`. Код был идентичен рабочему варианту, но с встроенным QWebEngineView перестал срабатывать (доставка сообщений Qt-окну зависит от жизненного цикла HWND и насоса сообщений — с QtWebEngine он устроен иначе; точную первопричину на вашей машине без удалённого доступа установить невозможно).

**Решение — не полагаться на Qt вообще:** горячие клавиши регистрируются на **собственном скрытом окне Win32 в отдельном потоке** с собственным циклом сообщений. Это работает одинаково на Windows 10 и 11, при любом фокусе (в том числе внутри браузера), при любом поведении Qt-окон. Дополнительно:
- если клавиша занята другим приложением — автоматическое периодическое повторное подключение + резервный опрос клавиатуры (GetAsyncKeyState) с защитой от дребезга;
- состояние видно в статусе и в логах (`hotkeys.registered`, `hotkeys.status`).

## 2. Как реализован голос (главное отличие версии)

В страницу **до её загрузки** вводится совместимый `SpeechRecognition`/`webkitSpeechRecognition` (если родного нет). Сайт видит «Chrome-совместимый» браузер, рисует кнопку микрофона и полный ввод/вывод. Диктовка работает по-настоящему:

```
сайт вызывает SpeechRecognition  →  мост QWebChannel (не блокируется CSP сайта)
    →  скрытый хост Windows PowerShell + System.Speech (штатный движок Windows)
    →  распознанный текст возвращается сайту → текст появляется в поле ввода
```

- **Работает на всех Windows 10/11**: PowerShell 5.1 и .NET System.Speech входят в состав Windows; никаких сторонних Python-пакетов и облаков.
- Речь **не покидает компьютер** (в отличие от Chrome, где диктовка идёт на серверы Google).
- Поддерживаются промежуточные (интерим) и финальные результаты, `continuous`, `interimResults`, стандартные события (`onresult`, `onerror`, `onend`…).
- Ошибка понятна: не установлен языковой пакет речи → `language-not-supported`; закрыт доступ приложений к микрофону → `not-allowed`.
- Если у сайта когда-то появится собственный рабочий распознаватель — шим не мешает (ставится только при отсутствии API, отключается переменной окружения `LEGAYZE_SPEECH=off`).

**Требования к голосу:** настройки Windows → «Конфиденциальность → Микрофон» → доступ для настольных приложений включён; установлен языковой пакет речи для нужного языка (для русского — «Речь» в компонентах языка). Точность распознавания Windows уступает облачному Google — это честная цена локальной работы; текст можно править в поле ввода перед отправкой.

Порядок работы с голосом прежний (ТЗ):
- **1-е нажатие** горячей клавиши (по умолчанию **F3**) → сайт начинает запись (кнопка микрофона найдена и «нажата» скриптом);
- **2-е нажатие F3** → отправка голосового запроса (кнопка отправки голоса/Enter).

Если кнопка всё же не найдена (сайт изменил DOM) — в статусе будет явное сообщение «Кнопка микрофона не найдена», а в логах `mic.button_missing`.

## 3. Почему именно эта архитектура (сравнение вариантов)

| Вариант | Итог |
|---|---|
| Portable Chrome + поиск HWND/SetParent (старый) | Работает по-разному у разных пользователей: права, авто-de-elevate, GPU, фокус, AV. Отклонён по вашему же требованию. |
| WebView2 (Edge) | Тот же Chromium, но: WebView2 Runtime ставится/обновляется на каждой машине отдельно, встраивание снова через чужой HWND и COM, SpeechRecognition в WebView2 не гарантирован. Сложнее и не стабильнее. |
| Playwright/Selenium | Внешний браузер + драйвер; тяжелее, те же проблемы внешнего окна. |
| **Qt WebEngine (выбран)** | Браузерный движок **поставляется вместе с приложением одинаковым на всех машинах**, окно — родной Qt-виджет без чужих HWND. Единственное, чего нет в движке — облачное распознавание речи, и этот пробел закрыт шимом + Windows Speech (раздел 2). |

Ограничение честно: движок внутри Qt WebEngine всё равно **Chromium** (просто встроенный и единый для всех). Совместимость с конкретным сайтом ИИ и входом Google остаётся внешней зависимостью; сайт может менять DOM. Гарантий «на все сайты и все аккаунты» не существует — есть воспроизводимое поведение и диагностика.

## 4. Установка и запуск (Windows 10/11 x64)

Python 3.12 x64, обычный запуск **без прав администратора**. CMD из этой папки:

```bat
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe main.py
```

Новые зависимости: `PyQt6-WebEngine` (браузер) и `PyQt6-WebChannel` (мост речи). Папка `chromium` не нужна.

### Быстрая проверка без входа в Google

```bat
.venv\Scripts\python.exe smoke_browser.py
```

Откроется локальная тестовая страница (поле ввода, кнопка микрофона, кнопка отправки) и проверятся: готовность страницы, поиск и «нажатие» кнопки микрофона, наличие Web Speech API и захвата аудио. Код возврата 0 — всё прошло. Сеть и аккаунт не нужны.

### Автотесты

```bat
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

22 теста: неизменность бизнес-логики, отсутствие внешнего браузера/SetParent, защита микрофона при очистке UI, JS-шим речи (Node.js), горячие клавиши, worker готовности. В среде разработки все 22 проходят.

## 5. Что осталось прежним

- GUI полностью: верхняя панель, плашки горячих клавиш, кнопки, стили, оверлей;
- авторизация Legalyze, HWID, шифрование настроек и промтов, миграция `%APPDATA%\Legalyze`;
- проверка версии на сервере (`SERVER_URL`, версия конфига 1.0.5), баланс, списание запросов, шаблон;
- выбор промта, подготовка PDF/TXT, подтверждение двух вложений, удаление файлов из чата;
- автоматизация сайта через CDP (подавление лишних элементов, клики кнопок) — **в прежнем виде**;
- горячие клавиши настраиваются как раньше (F2 — окно, F3 — микрофон, смена через плашки);
- одиночный запуск, логи в `%APPDATA%\Legalyze\logs`, `chrome_hwnd=null` в логах нормален.

Данные: конфиг/токен/промты/логи — прежние `%APPDATA%\Legalyze`; профиль браузера — отдельный `%APPDATA%\Legalyze\qtwebengine-profile`. Старый `chromium-profile` не используется. Вход в Google понадобится заново.

## 6. Что улучшено дополнительно

- **Совместимость User-Agent**: из UA убирается метка `QtWebEngine`, client hints (бренды) приводятся к Chrome — сайт не «урезает» интерфейс по признаку неизвестного браузера (`webengine.compat_installed`, `webengine.capabilities` в логах).
- **Очистка интерфейса** больше никогда не может скрыть панель ввода, микрофон, отправку, файлы и их иконки — только шапку Google, навигацию, меню аккаунта и снэкбары.
- Разрешение микрофона выдаётся автоматически для HTTPS-адреса страницы ИИ; камера и демонстрация экрана запрещены.
- Если кнопка микрофона/отправки не найдена — видимый статус ошибки вместо молчания.
- Горячие клавиши восстанавливаются сами (повторная регистрация каждые 10 с при конфликте).

## 8. Чек-лист приёмки на Windows 10 и 11

1. `smoke_browser.py` → `SMOKE OK`.
2. Запуск без администратора: вход в Google, главное окно, чат загружается, «лишние» элементы скрыты.
3. Кнопка микрофона **видна** в поле ввода; F3 — запись (индикация статуса), повторный F3 — отправка; текст диктовки появляется в поле ввода.
4. F2 скрывает и возвращает окно (в том числе при фокусе внутри браузера).
5. Выбор промта → экспорт PDF/TXT → два вложения → запрос → ответ → «КОНЕЦ ОТВЕТА».
6. Списание запроса и блокировка при нуле; смена горячих клавиш; перезапуск; закрытие без зависаний.
7. Логи `%APPDATA%\Legalyze\logs`: `hotkeys.registered` (или `hotkeys.status`), `webengine.capabilities`, `webengine.chat_ready`, `speech.started` при диктовке.

## 9. Известные ограничения

- Реальная отрисовка, Windows-сборка, микрофон и приёмка на ваших ПК **ещё не подтверждены** — прогон по чек-листу выше обязателен (в среде разработки нет Windows/GUI).
- Вход Google может ограничиваться для встроенных браузеров; подмены UA-токенов и обходов блокировок входа нет и не будет.
- Точность локального распознавания Windows зависит от установленного языкового пакета речи.
- Домен сайта ИИ может менять DOM — тогда правятся только JS-селекторы, бизнес-логика не затрагивается.
- Антивирусные предупреждения не гарантируются; решения по подписи — те же, что в `TestLegal/README.md`.

В `session.start`: `release_revision = universal-embedded-v1`.
