# Legalyze 1.0.5 — Universal v4: встроенный браузер + голос + горячие клавиши

Эталонная папка решения (анализ + лучшее решение). Рабочая логика Win10/Win11,
серверное взаимодействие, авторизация и основной GUI не менялись. Папки
`TestLegalUniversal/`, `TestLegalUniversal_v2/`, `TestLegalUniversal_v3/`
остаются нетронутыми как резервные копии; каждая новая правка выходит в новой
версионной папке `TestLegalUniversal_vN` (эта — `TestLegalUniversal_v4`).

**v4 исправляет дефекты по живым логам Windows 10 (build 19045):** нажатие
«Микрофон» вызывало «Восстановление ИИ» вместо диктовки (краш рендер-процесса
из-за нативного `SpeechRecognition`); при запуске был виден сырой браузер без
GUI (шторка оказалась под web-виджетом); на каждой загрузке падала сборка
скриптов (ошибка «not a function» и неработающий голосовой мост). Хоткеи
F2/F3 из v2 работают и не менялись.

## 1. Анализ причин дефектов

### Горячие клавиши: почему не срабатывали и всегда «конфликт»

Прежняя реализация (`win32_hotkeys.py`) строила **отдельный поток с невидимым
окном**: `CreateWindowExW` + `RegisterClassW` + цикл `PeekMessageW` +
`RegisterHotKey`, а события перекидывала в Qt сигналом из другого потока. Любая
ошибка в этом длинном пути (обрезание HWND/HINSTANCE на Win64 из-за
отсутствующих `argtypes`/`restype`, отказ `RegisterClassW`/`CreateWindowExW`,
гибель потока-демона) давала ровно наблюдаемую картину:

* `set_keys()` возвращал `False` → статус **«Конфликт горячих клавиш» при
  любой смене клавиши** (хотя конфликта не было);
* события не приходили вообще: поток мёртв → ни `WM_HOTKEY`, ни опрос.

**Решение (v2):** события клавиш получает **главный поток Qt** — `QTimer` (25
мс) вызывает `HotkeyMonitor.tick()`, который опрашивает `GetAsyncKeyState`
(с корректными `argtypes`/`restype`), детектирует фронт нажатия и сразу в
контексте GUI вызывает обработчик. Никаких потоков, скрытых окон, очередей
сообщений и маршалинга сигналов — отказаться не от чего. Это работает с любым
фокусом, поверх других окон и независимо от раскладки (физическое состояние
клавиатуры). Антидребезг — 350 мс на каждую клавишу отдельно.

`RegisterHotKey` сохранён **только как best-effort подавление** проброса
клавиши в другие приложения (чтобы F3 не попадал в браузер). Его отказ ничего
не блокирует и нигде не отображается: статус после смены клавиш всегда
«Готов к работе», ложный «Конфликт горячих клавиш» невозможен по построению.

### Микрофон: нажатие вызывало «Восстановление ИИ»

Симптомы (лог 2026-09-30): нажатие «Микрофон»/F3 → статус «Восстановление
ИИ…» вместо диктовки; повторное нажатие — снова восстановление.

Причина (по логу, **не** getUserMedia): `mic.dictation_started` → через 18 мс
`webengine.render_terminated CrashedTerminationStatus` → `crash_recovery`.
Рендер падал при `rec.start()` на **нативном** `window.SpeechRecognition`:
QtWebEngine 6.11 / Chromium 140 экспортирует конструктор, но штатный движок
распознавания требует Google API-ключа (`speech_recognition.cc`), которого нет
в этой поставке — старт распознавания убивает дочерний процесс. Штатная кнопка
микрофона сайта именно его и вызывала. Шим v3 намеренно не трогал нативный
конструктор («веб-STT не используем») — но его использует **сайт**.

Решение (v4), слоями:

1. **Шим всегда перехватывает `SpeechRecognition`/`webkitSpeechRecognition`:**
   нативный конструктор сохраняется в `window.__legalyzeNativeSpeechRecognition`
   (только диагностика) и **никогда не вызывается**; поверх ставится наш класс
   `window.LegalyzeSpeechRecognition` (QWebChannel → Windows System.Speech).
   Тест: нативный mock с `start() { throw }` — не вызывается ни разу.
2. **Перехват всех кликов по любой кнопке микрофона** (штатной или реплики):
   события pointer/mouse/click перехватываются в capture-фазе ДО обработчиков
   сайта (`preventDefault` + `stopImmediatePropagation`) и уводятся в
   НАСТОЯЩУЮ диктовку. Сайт не получает ни одного события → его
   `getUserMedia`/`SpeechRecognition` не вызываются → рендер не падает.
   Штатная кнопка микрофона остаётся на виду и реально работает.
3. **F3 сначала запускает нашу диктовку напрямую** (`JS_MIC_TOGGLE`); повторное
   нажатие/«Отправить»/Enter останавливает запись и отправляет запрос.
4. **Автовосстановление при сбое рендера** (до 3 раз) с остановкой висящих
   потоков, долбивших мёртвый CDP-сокет (шум `WebSocketConnectionClosed…`).
5. **Понятный статус** «Страница ещё загружается — подождите…», если микрофон
   нажат до готовности чата.

### Сырой браузер виден при запуске («нету поверх него GUI»)

Причина: шторка (`browser_cover`) создаётся в конструкторе окна, а браузер —
позже в `_start_chrome`; Qt кладёт более поздних детей **поверх** ранних, и
шторка оказывалась под web-виджетом. В v4 `_show_overlay` и `_start_chrome`
вызывают `browser_cover.raise_()`: до раскрытия по готовности (`loadFinished` +
250 мс) пользователь видит только шторку приложения, затем — уже зачищенную
страницу. Видимость элементов браузера исключена.

### Скрипты страницы: ошибка сборки «not a function» и глухой голосовой мост

IIFE-чанки бандла склеивались переводом строки; `})()` перед следующим чанком
`(() => …` разбирался как вызов → TypeError → хвост бандла (инициализация
QWebChannel) не выполнялся → `window.__legalyzeSpeechBridge` не создавался.
В v4 чанки склеиваются через `";\n"`, IIFE закрываются `;` — покрыто тестом.

### «Вечная прогрузка» на чистом %APPDATA%

Свежий профиль Google показывает межстраничник согласия, который прятался без
принятия и оставлял «вечную прогрузку». Теперь `CONSENT_AUTOCLICK_JS` нажимает
только кнопки согласия («Принять все»/Accept) и лишь затем элемент скрывается.

### Мигание элементов при запуске

Всё внедряется на `DocumentCreation` одним бандлом (UA/brand, голосовой мост,
автосогласие, рабочая кнопка микрофона, зачистка лишнего, канал Qt): лишние
элементы не появляются вовсе — приложение выглядит как сайт, а не как браузер.

## 2. Голос (как работает)

1. F3 (или кнопка микрофона) → штатный сценарий сайта находит кнопку
   микрофона (штатную или нашу реплику) и «кликает» её.
2. Наш мост QWebChannel (`legalyzeSpeech`) запускает диктовку Windows
   (`System.Speech`, русская/английская распознающая культура), стримит
   гипотезы и финальный текст.
3. `SpeechRecognition`-шим пишет текст в поле ввода (`textarea.ITIRGe` /
   `aria-label="Задайте вопрос"`).
4. Повторный F3 → штатный сценарий нажимает кнопку отправки (или Enter) —
   запрос уходит в чат ИИ.

Всё CSP-безопасно: только QWebChannel, без сетевых мостов. Если мост
недоступен — понятная ошибка через шим, без падений.

## 3. Почему эта архитектура

* Chromium/QtWebEngine без Google API-ключа **не умеет** штатный
  SpeechRecognition, и его `start()` даже **роняет рендер-процесс** (проверено
  по исходникам Chromium: `speech_recognition.cc` требует API key, и по логам
  пользователя) — поэтому наш шим **всегда** перехватывает конструктор, а
  распознавание идёт через Windows System.Speech;
  поэтому диктовка всегда идёт через Windows System.Speech.
* Нативное окно QtWebEngine обычно строится без WebRTC → `getUserMedia`
  недоступен (QTBUG-55108) — веб-диктовка сайта всё равно не заработала бы.
* Опрос `GetAsyncKeyState` из главного потока — единственный механизм хоткеев,
  у которого нет окна, потока и очереди сообщений, т.е. нечему ломаться.

## 4. Установка и запуск (Windows 10/11 x64)

```
py -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python main.py
```

`PyQt6-WebChannel` **не нужен** (не существует на PyPI): `PyQt6.QtWebChannel`
входит в базовый пакет PyQt6. При отсутствии официального `qwebchannel.js`
автоматически включается встроенная облегчённая реализация протокола.

### Быстрая проверка без входа в Google

```
.venv\Scripts\python smoke_browser.py
```

Локальная тест-страница проверяет: готовность страницы, поиск/клик кнопки
микрофона, поверхность Web Speech API, вставку реплики кнопки микрофона,
зум 67% (2/3). Exit code 0 = всё прошло.

### Автотесты

```
py -m unittest discover -s tests -v
```

31 тест: чистота поставки, неизменность бизнес-логики (байт-в-байт с
`TestLegal`/`TestLegalQtWebEngine`), корневые причины, опрос горячих клавиш
(фронт + антидребезг на клавишу), реплика кнопки микрофона (инъекция,
диктовка в поле ввода, остановка по отправке, приоритет штатной кнопки),
шим речи, зачистка DOM, автосогласие, протокол QWebChannel.

Логика авторизации, взаимодействие с сервером, основной GUI, выгрузка файлов,
все поля ввода/вывода, поведение Win10/Win11, `%APPDATA%\Legalyze`, общее

«конфликтов».

## 6. Что улучшено дополнительно

* Зум окна нативно 67% (`ZOOM_FACTOR = 2/3`), применяется и после каждой
  загрузки страницы.
* Логотип Google скрыт; интерфейс выглядит как сайт, а не как браузер.
* Свежий профиль: первый запрос работает без ручного «Принять все».
* Требования чистые: без несуществующих пакетов.
* Сборка скриптов страницы устойчива к ASI (чанки склеиваются через `;`),
  голосовой мост инициализируется на каждой загрузке.

## 8. Чек-лист приёмки на Windows 10 и 11

1. Зум 67% восстановлен; логотип скрыт; запуск без миганий.
2. F2 скрыть/показать окно — работает с любого фокуса и любой раскладки.
3. F3 — запись голоса: статус «Запись голоса…», текст идёт в поле ввода;
   повторный F3 отправляет запрос в чат ИИ.
4. Смена клавиш — статус «Готов к работе» (без «Конфликт горячих клавиш»).
5. Кнопка микрофона в панели ввода видна и работает (клик = запись и отправка
   промта); после нажатия статус «Запись голоса…», **не** «Восстановление ИИ».
6. Во время «Ожидание страницы ИИ…» элементы браузера не видны (только шторка
   приложения) — сырой браузер при старте не появляется.
7. Первый запрос на чистом профиле работает без ручного согласия.
8. Загрузка/выгрузка файлов, вход, поля — как в рабочей версии.

## 9. Известные ограничения

* Автоматизация зависит от DOM/логина/сети Google — при редизайне сайта
  селекторы нужно обновить (проверяйте диагностику в `%APPDATA%\Legalyze\logs`).
* Качество распознавания Windows System.Speech уступает Google ASR; для
  лучшего качества говорите чётко, в тихой комнате.
* Подавление проброса F2/F3 в другие программы — best-effort (если
  `RegisterHotKey` занят другим приложением, хоткеи клиента всё равно
  работают, но клавиша может достаться и фоновой программе).
* Штатный Web Speech API/getUserMedia в этой поставке QtWebEngine неработоспособен
  (и ронял рендер) — диктовка всегда идёт через Windows System.Speech через наш
  мост; при сбое рендера страница автоматически перезагружается (до 3 раз).
