# Legalyze 1.0.5 — Universal v2: встроенный браузер + голос + горячие клавиши

Эталонная папка решения (анализ + лучшее решение). Рабочая логика Win10/Win11,
серверное взаимодействие, авторизация и основной GUI не менялись. Папка
`TestLegalUniversal/` остаётся нетронутой как резервная копия предыдущей
версии; каждая новая правка выходит в новой версионной папке
`TestLegalUniversal_vN` (эта — `TestLegalUniversal_v2`).

**v2 исправляет единственный оставшийся дефект** (по итогам проверки на
Windows): горячие клавиши F2/F3 не срабатывали вообще, а любая смена клавиши
показывала «Конфликт горячих клавиш». Плюс восстановлена рабочая кнопка
микрофона в панели ввода.

## 1. Анализ причин дефектов

### Горячие клавиши: почему не срабатывали и всегда «конфликт»

Прежняя реализация (`win32_hotkeys.py`) строила **отдельный поток с невидимым
окном**: `CreateWindowExW` + `RegisterClassW` + цикл `PeekMessageW` +
`RegisterHotKey`, а события перекидывала в Qt сигналом из другого потока. Любая
ошибка в этом длинном пути (обрезание HWND/HINSTANCE на Win64 из-за
отсутствующих `argtypes`/`restype`, отказ `RegisterClassW`/`CreateWindowExW`,
гибель потока-демона) давала ровно наблюдаемую картину:

* `set_keys()` возвращал `False` → статус **«Конфликт горячих клавиш» при
  любой смене клавиши** (хотя конфликта не было);
* события не приходили вообще: поток мёртв → ни `WM_HOTKEY`, ни опрос.

**Решение (v2):** события клавиш получает **главный поток Qt** — `QTimer` (25
мс) вызывает `HotkeyMonitor.tick()`, который опрашивает `GetAsyncKeyState`
(с корректными `argtypes`/`restype`), детектирует фронт нажатия и сразу в
контексте GUI вызывает обработчик. Никаких потоков, скрытых окон, очередей
сообщений и маршалинга сигналов — отказаться не от чего. Это работает с любым
фокусом, поверх других окон и независимо от раскладки (физическое состояние
клавиатуры). Антидребезг — 350 мс на каждую клавишу отдельно.

`RegisterHotKey` сохранён **только как best-effort подавление** проброса
клавиши в другие приложения (чтобы F3 не попадал в браузер). Его отказ ничего
не блокирует и нигде не отображается: статус после смены клавиш всегда
«Готов к работе», ложный «Конфликт горячих клавиш» невозможен по построению.

### Кнопка микрофона: восстановлена и работает

Файл `html микрофон кнопка.txt` в репозитории **пуст (0 байт)** — кода кнопки
в нём нет. Реплика восстановлена по соседним выгрузкам DOM сайта (кнопка
отправки `html кнопка для отправки записи в ИИ чат.txt`, состояние записи
`html микрофон процесс записи.txt`) и по селекторам штатного сценария:

* разметка повторяет штатную кнопку сайта: `data-xid="input-plate-voice-button"`,
  `aria-label="Микрофон"`, Material-иконка микрофона (путь `M480-400…`),
  классы кнопки ввода **без** класса отправки (`wdK4Nc` специально исключён,
  чтобы `JS_STOP_AND_SEND` не принял кнопку за «Отправить»);
* кнопка вставляется в панель ввода автоматически (MutationObserver + таймер),
  **только если штатная кнопка сайта не найдена**; если штатная есть —
  работает она, реплика не мешает и удаляется;
* клик по кнопке (мышью или F3 через штатный сценарий — он находит реплику
  теми же селекторами) запускает **настоящую диктовку**: `SpeechRecognition` →
  наш мост QWebChannel → PowerShell `System.Speech` (Windows 10/11 без
  дополнительных зависимостей); текст пишется в поле ввода сайта, подсказка
  «Преобразование речи в текст…» и пульсация кнопки показывают запись;
* повторное нажатие останавливает запись; штатное нажатие «Отправить» (или
  Enter) тоже останавливает диктовку перед отправкой.

### «Вечная прогрузка» на чистом %APPDATA%

Свежий профиль Google показывает межстраничник согласия, который прятался без
принятия и оставлял «вечную прогрузку». Теперь `CONSENT_AUTOCLICK_JS` нажимает
только кнопки согласия («Принять все»/Accept) и лишь затем элемент скрывается.

### Мигание элементов при запуске

Всё внедряется на `DocumentCreation` одним бандлом (UA/brand, голосовой мост,
автосогласие, рабочая кнопка микрофона, зачистка лишнего, канал Qt): лишние
элементы не появляются вовсе — приложение выглядит как сайт, а не как браузер.

## 2. Голос (как работает)

1. F3 (или кнопка микрофона) → штатный сценарий сайта находит кнопку
   микрофона (штатную или нашу реплику) и «кликает» её.
2. Наш мост QWebChannel (`legalyzeSpeech`) запускает диктовку Windows
   (`System.Speech`, русская/английская распознающая культура), стримит
   гипотезы и финальный текст.
3. `SpeechRecognition`-шим пишет текст в поле ввода (`textarea.ITIRGe` /
   `aria-label="Задайте вопрос"`).
4. Повторный F3 → штатный сценарий нажимает кнопку отправки (или Enter) —
   запрос уходит в чат ИИ.

Всё CSP-безопасно: только QWebChannel, без сетевых мостов. Если мост
недоступен — понятная ошибка через шим, без падений.

## 3. Почему эта архитектура

* Chromium/QtWebEngine без Google API-ключа **не умеет** webkitSpeechRecognition
  (проверено по исходникам Chromium: `speech_recognition.cc` требует API key) —
  поэтому диктовка всегда идёт через Windows System.Speech.
* Нативное окно QtWebEngine обычно строится без WebRTC → `getUserMedia`
  недоступен (QTBUG-55108) — веб-диктовка сайта всё равно не заработала бы.
* Опрос `GetAsyncKeyState` из главного потока — единственный механизм хоткеев,
  у которого нет окна, потока и очереди сообщений, т.е. нечему ломаться.

## 4. Установка и запуск (Windows 10/11 x64)

```
py -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python main.py
```

`PyQt6-WebChannel` **не нужен** (не существует на PyPI): `PyQt6.QtWebChannel`
входит в базовый пакет PyQt6. При отсутствии официального `qwebchannel.js`
автоматически включается встроенная облегчённая реализация протокола.

### Быстрая проверка без входа в Google

```
.venv\Scripts\python smoke_browser.py
```

Локальная тест-страница проверяет: готовность страницы, поиск/клик кнопки
микрофона, поверхность Web Speech API, вставку реплики кнопки микрофона,
зум 67% (2/3). Exit code 0 = всё прошло.

### Автотесты

```
py -m unittest discover -s tests -v
```

31 тест: чистота поставки, неизменность бизнес-логики (байт-в-байт с
`TestLegal`/`TestLegalQtWebEngine`), корневые причины, опрос горячих клавиш
(фронт + антидребезг на клавишу), реплика кнопки микрофона (инъекция,
диктовка в поле ввода, остановка по отправке, приоритет штатной кнопки),
шим речи, зачистка DOM, автосогласие, протокол QWebChannel.

## 8. Чек-лист приёмки на Windows 10 и 11

1. Зум 67% восстановлен; логотип скрыт; запуск без миганий.
2. F2 скрыть/показать окно — работает с любого фокуса и любой раскладки.
3. F3 — запись голоса: статус «Запись голоса…», текст идёт в поле ввода;
   повторный F3 отправляет запрос в чат ИИ.
4. Смена клавиш — статус «Готов к работе» (без «Конфликт горячих клавиш»).
5. Кнопка микрофона в панели ввода видна и работает (клик = запись).
6. Первый запрос на чистом профиле работает без ручного согласия.
7. Загрузка/выгрузка файлов, вход, поля — как в рабочей версии.

## 9. Известные ограничения

* Автоматизация зависит от DOM/логина/сети Google — при редизайне сайта
  селекторы нужно обновить (проверяйте диагностику в `%APPDATA%\Legalyze\logs`).
* Качество распознавания Windows System.Speech уступает Google ASR; для
  лучшего качества говорите чётко, в тихой комнате.
* Подавление проброса F2/F3 в другие программы — best-effort (если
  `RegisterHotKey` занят другим приложением, хоткеи клиента всё равно
  работают, но клавиша может достаться и фоновой программе).
