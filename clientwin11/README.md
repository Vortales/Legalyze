# Legalyze: диагностический клиент Windows 10 / Windows 11

Это **самостоятельная копия клиентской части**, а не отдельный тест встраивания. Авторизация, привязка HWID, баланс, шаблоны, промты, микрофон и загрузка файлов сохранены. Исходные `client/`, сервер и `client_diagnostics/` не изменены.

**Важно:** исправлены обнаруженные дефекты кода, но воспроизведения на конкретном компьютере Windows 11 пока нет. Нельзя считать причину подтверждённой или совместимость со всеми сборками Windows проверенной до запуска на целевой машине.

## Быстрый запуск

1. Используйте Windows 10/11 x64 и Python **3.11 или 3.12 x64**. Для первого сравнения берите одинаковые Python, Qt и portable Chromium на обеих ОС.
2. Скопируйте **всю** папку `clientwin11` на компьютер. Положите вашу полную рабочую portable-сборку Chromium в `clientwin11\chromium\` (не один `chrome.exe`, а все DLL, ресурсы и подпапки). Chromium в репозитории отсутствует; `chromium.txt` — не исполняемый браузер.
3. В командной строке, находясь в `clientwin11`:

```bat
py -3.11 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe main.py
```

Далее можно запускать `run_diagnostic.bat`. **Не запускайте от администратора**, если обычный клиент не требовал этого: разный уровень прав мешает корректному сравнению.

Пароль/токен из исходного `client/config.json` намеренно **не перенесены**. Не распространяйте исходный конфиг с чужими сохранёнными учётными данными. Войдите заново; может также потребоваться вход в Google в новом профиле браузера и выбор промта.

### Где находятся данные

| Данные | Расположение |
|---|---|
| Конфиг, шаблон, кэш | `%APPDATA%\Legalyze` |
| Профиль Chromium | `%APPDATA%\Legalyze\chromium-profile` |
| Логи каждой отдельной сессии | `%APPDATA%\Legalyze\logs\дата-время-pid-id` |
| Сохранённые старые данные при конфликте | `%APPDATA%\Legalyze\migration-backups` |

По требованию пользователя хранилище **теперь общее с обычным клиентом**. Не запускайте старую и новую версии одновременно. Существующие конфиг и шаблон `Legalyze` имеют приоритет; файлы с теми же именами из диагностической версии сохраняются в резервной копии, а не перезаписывают их. Профиль обычного клиента `GoogleAIWindow` не переносится и не изменяется.

Перед первым запуском закройте старые версии Legalyze и принадлежащие им Chromium. При запуске автоматически переносятся старые каталоги `%APPDATA%\LegalyzeWin11`, `%LOCALAPPDATA%\LegalyzeWin11` и `%TEMP%\LegalyzeWin11`, если они существуют. Старый `Profile` становится `Legalyze\chromium-profile`, если целевого профиля ещё нет. Профили **никогда не объединяются**. Старые журналы попадают в `Legalyze\logs\imported-*`; остальные исходные файлы сохраняются в `migration-backups`. После успешного переноса прежних каталогов нет; приложение их больше не создаёт. Старые исполняемые версии, если их запустить отдельно, всё ещё могут создавать свои прежние каталоги — обновите все используемые копии.

При занятом профиле, недоступной проверке процессов, перенаправленном каталоге или ошибке перемещения между дисками перенос останавливается без принудительного удаления. Уже перенесённые файлы сохраняются; незавершённый перенос продолжается при следующем запуске. При разных дисках потребуется ручной перенос после закрытия приложений. Не удаляйте старые данные, пока не проверены конфиг и профиль.

Новые логи не записываются в Local/Temp: если `%APPDATA%\Legalyze\logs` недоступен для записи, запуск завершается ошибкой. Повторный запуск диагностического клиента блокируется через `QLockFile`. Не удаляйте lock-файлы работающего приложения.

## Найденные причины и внесённые изменения

### 1. Главное окно за пределами экрана — наиболее прямое объяснение симптома

В исходном `MainWindow` использованы `X=1426`, `Y=200`, `W=453`, `H=735`. Это **логические координаты Qt**. Например, при дисплее 1920×1080 и масштабе 150% доступная ширина составляет примерно 1280 логических пикселей: окно начинается за правым краем. Дополнительно `Qt.Tool` не даёт обычной кнопки на панели задач. Процесс Chromium при этом вполне может работать.

Исправление: главное окно — `Qt.Window`, размещается внутри `availableGeometry()` основного монитора, выводится на передний план. В лог попадают геометрия, DPR и доступные области всех экранов. Существующая фиксированная вёрстка 453×735 сохранена; на крайне маленькой рабочей области окно прижимается к верхнему краю, но полный редизайн компактной вёрстки здесь не выполнен.

### 2. Chromium намеренно скрыт, показ связан с сетью

Исходный запуск использовал `SW_HIDE` и `--window-position=-32000,-32000`. Затем последовательно выполнялись CDP, разрешения, JS и до 150 итераций DOM-проверок, в каждой — потенциально два запроса по 5 секунд. Это не гарантированные «15 секунд». Только потом искалось окно.

Исправление: Chromium сохраняет WS_VISIBLE, но в обычном режиме стартует за пределами виртуального рабочего стола; принадлежащее ему окно ищется до CDP и встраивается отдельным сигналом. DOM-ожидание ограничено монотонным дедлайном; WebSocket connect имеет таймаут, ожидание CDP-lock также ограничено. Закрытый WebSocket больше не вызывает цикл повторных чтений до таймаута. Предыдущие диагностические ревизии намеренно показывали браузер отдельно на старте; в текущей ревизии это поведение оставлено только в режиме LEGALYZE_EXTERNAL_BROWSER=1.

### 3. Неверный выбор HWND и непроверенный SetParent

Старый поиск допускал чужие окна Chromium и некоторые окна нулевого размера. HWND передавался через `pyqtSignal(int)`, то есть 32-битный тип, хотя HWND имеет размер указателя.

Исправление: только PID собственного дерева, достаточно большое окно, предпочтение видимому; сигнал `object` не сужает HWND. Журналируются PID, размеры, класс, стили, видимость, родитель, DPI/awareness. Встраивание меняет стиль перед `SetParent`, сбрасывает `LastError`, проверяет фактический `GetParent`. Нулевой результат `SetParent` сам по себе **не ошибка**, если прежним родителем был desktop.

При отказе встраивания стили восстанавливаются, Chromium возвращается в отдельное видимое окно, показывается сообщение с каталогом логов. Различия DPI-awareness/UIPI — **гипотезы**, не установленный факт. Не применяются `--no-sandbox`, отключение защит Windows или принудительная подмена DPI всех процессов.

### 4. Другие точки задержки

- Проверка обновления происходит после авторизации и до главного окна. Сохранена политика сервера о необходимости обновления; этап журналируется; при требовании выхода есть событие `update.required_exit`. Промежуточный диалог состояния убран по просьбе пользователя.
- Загрузка шаблона из сети вынесена из конструктора GUI в QThread; применение данных выполняется в GUI-потоке.
- CDP localhost-запросы не идут через HTTP-прокси; WebSocket также исключает localhost из proxy.
- Профиль Chromium отделён от обычного клиента, повторный запуск ограничен. При передаче запуска уже существующему процессу и раннем выходе будет событие `chromium.early_exit`.
- Ошибки HWID-команд (включая отсутствие WMIC), криптографии, конфигурации, ресурсов, обновления и сетевых запросов больше не исчезают бесследно. Алгоритм HWID не заменён, чтобы не ломать существующие привязки.

## Состав диагностики

- `diagnostic.jsonl`: время, поток, события начала/окончания этапов, длительность, исключения (тип, errno/winerror, стек без локальных переменных и текста исключения), авторизация/HWID/balance **без учётных данных**, статусы и длительность HTTP, имена CDP-методов/коды ошибок без JS и содержимого ответов.
- Информация об ОС/сборке, Python/архитектуре, Qt и пакетах, экранах, правах, RDP, наличии переменных proxy; GPU и версия драйвера через ограниченный по времени фоновый PowerShell. Нет дампа всего окружения, аппаратных серийных номеров или списка чужих процессов.
- Путь, размер и SHA-256 `chrome.exe`, аргументы запуска, PID, CDP browser/protocol version при успешном подключении, дерево PID и кандидаты HWND.
- `main.snapshot` каждые 5 секунд: видимость/геометрия главного окна, overlay, состояние QThread и код завершения Chromium. `gui.heartbeat` независимо от GUI каждые 10 секунд.
- `stacks.log`: faulthandler для Python/native аварий, один снимок через 60 секунд от старта (даже при зависании импорта), до 20 дополнительных снимков при отсутствии GUI heartbeat более 15 секунд. Стек не содержит локальные переменные.
- `chromium.log`, `chromium-stdout.log`, `chromium-stderr.log`: собственный вывод браузера, когда Chromium его создаёт. Некоторые сборки Chromium не создают все эти файлы.

Основной журнал ротируется: 8 MiB × 5 файлов на сессию. Повторяющиеся исключения прореживаются (первые три и затем степени двойки; поле `occurrence`). Каждая строка основного журнала — JSON с UTC-временем и именем потока. Сырые браузерные файлы не ротируются приложением; каталог сессий автоматически не удаляется, контролируйте свободное место и очищайте старые сессии вручную.

**Конфиденциальность:** приложение намеренно не пишет пароли, JWT, Authorization, HTTP-тела, содержимое промтов/PDF, HWID, текст страниц и заголовки окон. Но нативные логи Chromium и сообщения Qt могут содержать URL, пути профиля, имя пользователя Windows и другие данные. Перед отправкой кому-либо просмотрите файлы и удалите чувствительные сведения. Это не гарантированно обезличенный архив. Полный дамп памяти не создаётся. При принудительном завершении процесса ОС/антивирусом финального события может не быть.

## Как установить причину на проблемном ПК

Сначала запустите обычный режим, воспроизведите сбой, подождите **60–90 секунд**, затем закройте клиент. Запишите время, Windows build, разрешение, масштаб, число мониторов и результат. Сохраните каталог этой сессии. Следующие проверки делайте **по одной**, закрывая предыдущий экземпляр.

Команды ниже — для `cmd.exe` из `clientwin11`; после каждой проверки очистите переменную через `set ИМЯ=`:

```bat
rem A: исключить GPU/драйвер
set LEGALYZE_DISABLE_GPU=1
.venv\Scripts\python.exe main.py
set LEGALYZE_DISABLE_GPU=

rem B: исключить SetParent/встраивание (браузер отдельным окном)
set LEGALYZE_EXTERNAL_BROWSER=1
.venv\Scripts\python.exe main.py
set LEGALYZE_EXTERNAL_BROWSER=

rem C: исключить блокировку/повреждение профиля (потребуется новый вход в Google)
set LEGALYZE_FRESH_PROFILE=1
.venv\Scripts\python.exe main.py
set LEGALYZE_FRESH_PROFILE=
```

Чистый профиль создаётся как `Profile-<id сессии>` и не удаляется автоматически. Эти же переменные поддерживаются собранным exe вместо команды Python.

| Последний этап / наблюдение | Что проверять |
|---|---|
| Нет `session.start` | запуск самого exe/распаковка, SmartScreen, антивирус, зависимости, консоль сборки |
| Нет `auth.accepted` | этап авторизации, HWID, сохранение конфигурации; HTTP status/stack |
| `auth.accepted`, нет `main.shown` | проверка версии, диалог шаблона, `MainWindow.__init__`, stacks |
| Есть `main.shown`, окно не видно | `main.geometry`, `main.snapshot`, DPI, экран, visibility; действия hotkey |
| `chromium.early_exit` | профиль занят, запуск передан другому экземпляру, авария или запрет; код и stderr |
| Нет HWND за 25 секунд | `win32.scan`, жив ли PID, нативный лог Chromium, AV/EDR |
| `embed.SetParent` с неверным `actual` | error, awareness/DPI родителя и браузера, сравнение с B |
| HWND встроен, нет `cdp.discovered` | порт DevTools, политики Chromium/EDR, локальная сеть, чистый профиль |
| `cdp.protocol_error` / `CDP.send` | конкретный метод, код, версия Chromium; не обязательно Windows |
| Работает только A | GPU/драйвер/композитинг — кандидат, не автоматическое доказательство |
| Работает только C | состояние/конкурентное использование профиля — кандидат |
| `gui.heartbeat age_seconds > 15` | соответствующие Python-стеки: что блокирует GUI |

Для сравнения Win10/Win11 используйте одинаковую portable-сборку браузера: SHA-256 записывается в лог. Сохраните версии пакетов: `.venv\Scripts\python.exe -m pip freeze > tested-environment.txt`. Требования здесь задают диапазоны, а не заявляют заранее проверенную фиксированную сборку.

## Сборка exe

Для диагностики предпочтительнее **standalone/onedir + консоль**, а не onefile: меньше неопределённости из-за распаковки и антивируса. Выполняйте сборку **на Windows** из активированного окружения:

```bat
call .venv\Scripts\activate.bat
python -m pip install pyinstaller
build_pyinstaller.bat
```

Результат: `dist\LegalyzeWin11\LegalyzeWin11.exe`. Скопируйте всю папку `dist\LegalyzeWin11`, затем добавьте в неё `chromium\`. Qt DLL и плагины из `_internal` тоже нужны.

Альтернатива: `python -m pip install nuitka ordered-set zstandard`, затем `build_nuitka.bat` (нужен поддерживаемый компилятор). Chromium положите в `build\main.dist\chromium`. Обе сборки включают шрифт; паковать исходные учётные данные не нужно. Windows-сборки в текущей Linux-среде **не выполнялись**.

## Исправление по логу Windows 11 от 28.09.2026

В логе нажатие «Войти» заканчивалось `TypeError` внутри `diagnostics.stage`, до HTTP-запроса авторизации. Причина воспроизведена отдельным тестом QtCore: `clicked(bool)` передавал аргумент `checked` в обёртку `(*args, **kwargs)`, которая вызывала исходный `_do_login(self)` с лишним аргументом. `functools.wraps` не восстанавливает для Qt реальную сигнатуру Python-функции.

Добавлены явные `@pyqtSlot()` **над** `@stage` для входа, закрытия, перезапуска и других безаргументных Qt-обработчиков. Проверены сигналы с `False`, `True` и прямой вызов, как при Enter. Не применяется небезопасный повторный вызов обработчика после TypeError: это могло бы повторить сетевой запрос или скрыть ошибку внутри тела функции. Диагностика теперь отдельно фиксирует несовпадение числа аргументов без записи их значений; штатный SystemExit имеет событие `stage.exit`, а не «exception». Для инвентаризации PowerShell явно выставлена UTF-8 кодировка.

Для исправления текущей установленной версии замените `main.py` и `diagnostics.py` файлами из этой папки, полностью закройте предыдущий экземпляр и запустите заново. Переустановка Chromium, удаление профиля или отключение антивируса для исправления этого TypeError не нужны.

Другие наблюдения из предоставленного лога:
- Рабочая область 1024×720: исходный X=1426 действительно находится за экраном. Новая версия размещает окно иначе; фиксированная высота 735 всё ещё немного превышает доступную высоту.
- WMIC не найден (WinError 2), оба PowerShell-запроса HWID превышают 5 секунд. Это задерживает конструктор окна входа примерно на 10 секунд и приводит к резервным значениям идентификаторов. Это отдельная проблема; алгоритм привязки в этом исправлении не менялся.
- `InvalidToken` в `decrypt_secret` означает невозможность расшифровать сохранённый пароль текущим ключом, а не отказ сервера авторизации. Возможные причины — перенос конфигурации, повреждение данных либо изменение машинных составляющих ключа. Введите пароль вручную; пока HWID нестабилен, не полагайтесь на сохранение пароля. Не сбрасывайте серверную привязку без отдельной проверки.
- Microsoft Basic Display Adapter делает GPU-проверку полезной на следующем этапе, но не объясняет данный TypeError: Chromium в показанной сессии ещё не запускался.

После повторного входа нужны события `auth.result`, `auth.accepted`, `main.shown`, `chromium.spawned`, `embed.SetParent` и последующие ошибки, если они будут. Фактическая совместимость с этой Windows/Qt/Python всё ещё требует повторного запуска на машине пользователя.


## Исправление по следующему логу: отдельное белое окно и вечный экспорт

В сессии `20260928-235338-940-267384` авторизация успешна, главное окно показано, CDP подключён к Chrome 151.0.7922.34. `SetParent` успешен, DPI-awareness у обоих окон равен 2. Это не подтверждает конфликт DPI в этой сессии.

Но выбирался HWND 197284: **невидимый `Chrome_WidgetWin_0`**, первый достаточно большой кандидат. Код не ожидал настоящего видимого окна приложения. Это дефект выбора, хорошо согласующийся с отдельным окном и пустой встроенной поверхностью; окончательно проверить результат нужно на Windows. Теперь допускается только видимый `Chrome_WidgetWin_1` собственного процесса/потомков без родителя и с ненулевой площадью, причём один HWND должен пройти три последовательных сканирования. Если сборка браузера не создаёт такой класс, за 25 секунд будет явная ошибка и журнал кандидатов, а не захват `_0` наугад.

Изменения:
- CDP-опрос завершения ответа убран из GUI-потока. Одновременно разрешён только один фоновый запрос; результат применяется Qt-слотом. До подтверждённого прикрепления файлов этот опрос не запускается.
- Изменение геометрии встроенного браузера запрашивается с `SWP_ASYNCWINDOWPOS`, чтобы не ждать обработки его оконным потоком. Лог `embed.geometry_requested` — снимок сразу после запроса, не гарантия, что асинхронное перемещение уже завершилось.
- Добавлены `prompt.prepared`, `upload.state`, `upload.attempt`, `upload.attachments_confirmed`, `page.probe`. Проба страницы каждые 5 секунд пишет только фиксированную категорию сайта, readyState и числовые количества элементов: без URL, текста, названий файлов и содержимого документов. `injected=true` означает лишь успех попытки передачи в DOM, не подтверждение загрузки сервером Google.
- Цикл ожидания неподтверждённых файлов имеет 90-секундный дедлайн, проверяемый между операциями; дополнительный GUI-таймер через 120 секунд запрашивает остановку и выводит понятную ошибку. Уже выполняющийся блокирующий вызов нельзя мгновенно прервать этим таймером; при остановке запрещаются последующие попытки передачи файлов. Состояние «файлы прикреплены» при таймауте не выставляется. Для новой попытки после зависшего вызова перезапустите клиент.
- Во время закрытия остановлены GUI-таймеры и очищен HWND до уничтожения Chromium: `WinError 1400` в конце присланного лога относится к уже закрытому окну, а не к причине первоначального белого экрана.
- В `chromium.spawned` PID браузера теперь называется `browser_pid`, чтобы не перезаписывать общий PID процесса клиента.

Для этой правки замените **`main.py` и `win32_diagnostics.py`**, сохранив обновлённый `diagnostics.py` из предыдущего исправления. Сначала повторите обычный запуск. Если окно остаётся белым, отдельно проверьте `LEGALYZE_DISABLE_GPU=1`, затем отдельный запуск с `LEGALYZE_EXTERNAL_BROWSER=1`. Не отключайте sandbox или защиты Windows.

Успешные ответы CDP и `readyState=complete` сами по себе не доказывают загрузку нужного чата: это может быть страница входа/согласия/ошибки. Если ожидание файлов остаётся, нужны новые `page.probe`/`upload.state`, `chromium.log` и **`stacks.log`**. Интервал, когда запрос с таймаутом 1 секунда занял около 29 секунд, требует стека и проверки нагрузки/пауз виртуальной машины; один лог не позволяет приписать его исключительно сети, GPU или конкретному Python-вызову. HEAD промта выполнялся в рабочем потоке — его задержка сама по себе не объясняет блокировку GUI.

Тесты воспроизводят отказ от скрытого `_0` из присланного лога, проверяют одновременность не более одного фонового опроса, защиту содержимого страницы в диагностике и завершение цикла по дедлайну. Windows end-to-end проверка остаётся за целевой машиной. Неустойчивое получение HWID и расшифровка старого пароля остаются отдельными проблемами: в этой правке машинный ключ/привязка не изменены.


## Доработка после успешного запуска: без промежуточных окон и передача фокуса

Лог `20260929-000949-6112-429465` подтверждает выбор видимого `_1`, успешное встраивание, `upload.attachments_confirmed: true`, скрытие overlay и фоновый ResponsePoll без прежнего зависания. Пользователь подтвердил корректное отображение и экспорт PDF/TXT.

Изменения обычного режима:
1. **Нет намеренного появления Chromium на рабочем столе.** Браузер стартует с координатами на 8192 единицы левее/выше начала всего виртуального рабочего стола (учтены мониторы с отрицательными координатами), с `SW_SHOWNOACTIVATE`. Это сохраняет `WS_VISIBLE`, выбор настоящего `_1` и загрузку Chromium: не используются SW_HIDE/минимизация, которые могли бы сломать предыдущий фикс. После выбора HWND окно перемещается внутрь GUI. Режим `LEGALYZE_EXTERNAL_BROWSER=1` по-прежнему намеренно показывает отдельное окно. Chromium должен соблюдать свой `--window-position`; нативную проверку отсутствия вспышки нужно выполнить на целевой сборке, особенно если она восстанавливает положение окна из профиля.
2. **Удалён отдельный диалог «Legalyze — запуск».** Проверка версии сохранена и журналируется; при медленной сети между авторизацией и главным окном возможна пауза без дополнительного окна. Сообщение о действительно обязательном обновлении не удалено.
3. **Добавлена явная передача нативного клавиатурного фокуса Chromium.** Клик по дочернему окну браузера обрабатывается мостом `browser_focus.py`: проверяются принадлежность HWND и foreground, на время SetFocus соединяются очереди ввода соответствующих потоков через AttachThreadInput, затем обязательно разъединяются в finally. Уже правильно установленный фокус не меняется. Фокус не перехватывается на каждом тике таймера, при кликах по Qt-кнопкам/диалогам, при overlay или переключении в другую программу. Снят возможный WS_EX_NOACTIVATE у встраиваемого браузера; временный LoadingOverlay остаётся неактивируемым.

Мост проверяет только переход состояния **левой кнопки мыши** таймером Qt 30 мс и HWND под указателем. Он не устанавливает клавиатурный перехватчик, не перехватывает текст и не пересылает WM_CHAR/искусственные нажатия: раскладки, clipboard и IME должны обрабатываться самим Chromium. Очень короткий клик между тиками или блокировка GUI могут быть пропущены; при отсутствии `focus.handoff` повторите клик и приложите журнал. Кнопки микрофона и глобальные горячие клавиши не изменены.

**Для обновления нужны три файла:** `main.py`, `win32_diagnostics.py` и **новый `browser_focus.py`**. Остальные файлы предыдущей версии сохраните. При exe-сборке пересоберите приложение (PyInstaller/Nuitka подхватят импорт нового модуля).

Проверка на Windows: дождаться экспорта → кликнуть в редактор чата → набрать русский и английский текст, Backspace и Ctrl+V → открыть/закрыть «Шаблон» и повторить → скрыть/показать горячей клавишей и повторить. Также убедиться, что кнопки Qt продолжают работать и фокус другой программы не перехватывается. Если ввод не появился, пришлите `focus.handoff`, `focus.detach`, `focus.skipped`, `focus.already_owned` и `page.probe` после клика. В page.probe добавлены только булевы признаки documentFocused, activeEditable, activeReadOnly, activeDisabled; текст и значения полей не записываются.

Тесты проверки очередей ввода используют подставные Win32 API (включая разъединение при исключении и запрет перехвата foreground); они **не подтверждают** исправление клавиатуры на Windows без повторного запуска. Точная причина потери фокуса в предыдущем логе не была записана — это адресное исправление и диагностика, а не заявление о доказанном исправлении всех вариантов IME/Qt/Chromium.

## Обновление: elevated Win10 / автоматический перезапуск Chromium

Повторный журнал Win10 (PID клиента 8424) показал `elevated: true`, выход стартового Chromium с кодом 0 через ~0,21 с и 11 процессов с тем же профилем **после** запуска. Последняя проверка сама по себе не доказывает, что браузер был открыт заранее: процессы могли появиться при автоматическом перезапуске с понижением прав. Chromium имеет такой механизм (`MaybeAutoDeElevate`); см. [разбор аналогичного сбоя](https://github.com/vercel-labs/agent-browser/issues/1406) и [исходный код Chromium](https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/chrome_browser_main_win.cc).

Исправление ограничено **Windows 10 Desktop с повышенными правами**:

1. До изменения настроек профиля и до создания процесса проверяется, не занят ли профиль. При занятом профиле выводится отдельная ошибка с актуальными PID, без завершения чужих процессов.
2. Chromium сразу запускается через `CreateProcessWithTokenW` с неповышенным токеном оболочки рабочего стола. Проверяются совпадение пользователя (SID), сессии и отсутствие повышения у целевого токена. Чужая учётная запись не используется. Пароли не запрашиваются.
3. Сохраняется настоящий HANDLE и PID созданного процесса. По ним работают прежние поиск дочерних процессов, проверка HWND и завершение. Существующие браузеры не подхватываются по одному лишь совпадению профиля; PID не открывается повторно при завершении.
4. Нет `--no-sandbox`, `--do-not-de-elevate` или отключения UAC. Offscreen-позиция, `SW_SHOWNOACTIVATE`, три стабильных сканирования HWND и мост фокуса сохранены.
5. Если безопасный запуск недоступен (нет desktop shell, другая учётная запись, отказ API), автоматического отката к повышенному Chromium нет: сообщение предлагает запустить Legalyze и IDE без прав администратора.

**Windows 11 и неповышенный запуск Windows 10 продолжают использовать прежний `subprocess.Popen`** с теми же аргументами и перенаправлением stdout/stderr. В новом токенном пути stdout/stderr не наследуются; собственный журнал Chromium по-прежнему пишется в `chromium.log`. События `chromium.launch_policy`, `chromium.profile_before_launch`, `chromium.desktop_token_launch` позволяют проверить выбранный путь и PID. SID, токены и содержимое командных строк проверяемых процессов не записываются.

**Обновление с c92d7ff:** замените `main.py` и обязательно добавьте `browser_process.py` рядом с ним; для EXE выполните пересборку. Остальные модули предыдущей версии, включая `storage_paths.py`, обязательны и остаются на месте.

Перед первой проверкой закройте оставшийся после предыдущих неудачных запусков Chromium с профилем `%APPDATA%\Legalyze\chromium-profile` (в диспетчере задач можно показать столбец «Командная строка»). Не завершайте все процессы Chrome наугад и не используйте старые PID из журнала: они могут быть переиспользованы. Альтернатива для очистки оставшихся процессов — перезагрузка Windows. После запуска ожидаются `chromium.desktop_token_launch` → `win32.window_selected` → подключение CDP. При сбое нужны новый `diagnostic.jsonl` и `chromium.log` из папки текущей сессии; проверьте браузерный журнал на личные данные перед отправкой.
